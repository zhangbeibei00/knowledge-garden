# 🕰️ 投机解码技术编年史

> 从 2023 的原始 SD → 2024 的 Medusa / EAGLE → 2024 末的 MTP → 2026 的 DFlash / DSpark / JetSpec，
> 这条技术脉络本质上是在 **"起草有多快"（↓T_draft）** 和 **"猜得有多准"（↑τ）** 两个变量间反复寻找新平衡点。

## 为什么大模型说话这么慢？

大家在用大模型时，会发现模型"打字"（逐词生成回答）很慢，一个字一个字往外蹦。

原因在于自回归（autoregressive）生成的本质：每生成一个 token，都要把前面的内容完整计算一遍。模型生成第 N 个词，必须先看到第 N-1 个词；生成第 N-1 个词，又必须先看到第 N-2 个词。

**投机解码（Speculative Decoding，SD）** 就是解决这件事的标准思路。它的核心思想极其朴素，甚至有点像职场里的场景：

> 让一个快速的「实习生」（draft model）先把接下来几句话都写好，再让贵重的「老板」（target model）一次性扫一眼、批量核对。老板一次前向传播就能同时验证好几个词对不对，蒙对的词直接照单全收，蒙错的地方老板自己再改。

这套思路最早由 Google 的 Leviathan et al.（*Fast Inference from Transformers via Speculative Decoding*, 2023）和 DeepMind 的 Chen et al.（*Accelerating Large Language Model Decoding with Speculative Sampling*, 2023）几乎同时提出。

它有一个很优雅的数学保证：通过改良版的拒绝采样（modified rejection sampling），最终生成的文本分布和老老实实用大模型逐词采样**完全等价**——这叫"**无损（lossless）加速**"，不是近似、不是蒸馏，是数学上可以证明分布不变的加速。

加速收益可以用一个简单公式概括：

$$
L = \frac{T_{draft} + T_{verify}}{\tau}
$$

其中 $T_{draft}$ 是生成草稿的时间开销，$T_{verify}$ 是大模型验证一批草稿的时间开销，$\tau$ 是平均每轮被接受的 token 数（包括验证时大模型顺带白送的 bonus token）。

想让 $L$ 更小，无非两条路：

- **增大分母**：让 $\tau$ 更大（草稿质量更高，猜得更准）
- **减小分子**：让 $T_{draft}$ 更小（起草更便宜）

接下来的 EAGLE / MTP / DFlash / DSpark / JetSpec，本质上都是在这两个变量之间反复横跳、寻找最优解。

## 一：从独立小模型到自我投机（2023 → 2024）

最早期的投机解码是找一个独立训练的小模型当草稿模型，业界普遍做法是用同系列的小模型给大模型当草稿（比如用 LLaMA-7B 给 LLaMA-70B 起草）。

但这样有问题：**小模型要单独训练、单独维护一套词表和 KV Cache，工程上很重，而且小模型和大模型的「思路」可能对不上，猜中率不高。**

于是社区很快演化出"自我投机"（self-speculation）路线：不再找一个完全独立的模型，而是在大模型自己身上"长"出一个轻量级的起草头。

**Medusa** 是这条路线的代表作之一：在大模型最后一层之上加上多个可以并行解码的头，每个头负责预测未来第 k 个位置的 token，一次推理就能吐出好几个候选词。但因为 Medusa 的每个并行头之间是相互独立的，位置之间缺乏依赖关系，生成的草稿 token 质量非常有限。

真正把这条路线的潜力打开的，是 EAGLE。

---

## 二：EAGLE 三部曲 —— 把"猜词"变成"猜特征"（2024 → 2025）

EAGLE（Extrapolation Algorithm for Greater Language-model Efficiency）由北大团队（Yuhui Li 等）提出，从 EAGLE-1（ICML'24）到 EAGLE-2（EMNLP'24）再到 EAGLE-3（NeurIPS'25），是过去两年投机解码领域当之无愧的"标杆"。

### EAGLE-1：不猜 token，猜"特征"

EAGLE-1 的核心改变：**与其在 token 这个离散、高度随机的空间里做自回归预测，不如在大模型内部的连续特征（feature）空间里做自回归预测**。

具体来说，EAGLE 复用大模型**倒数第二层**的隐藏状态（top-layer feature），训练一个很小的草稿模型，让它学会"外推"下一个位置的特征向量，然后再过一个共享的 LM head 把特征转成 token 分布。

一个关键工程细节：**单纯根据当前特征预测下一个特征存在很大的不确定性**（比如"我"后面可能接"是"也可能接"爱"）。EAGLE 的解法是把**当前采样出来的 token 的词向量**也一起喂给草稿模型，用"已知的具体词 + 抽象特征"联合条件化。

EAGLE-1 的提升非常明显：草稿模型只有一层 Transformer，8 张 RTX 3090 训一两天就能搞定，相比传统投机解码能带来约 2-3 倍的速度提升，且可以和 vLLM、SGLang、DeepSpeed 等并行框架无缝组合。

### EAGLE-2：草稿树

EAGLE-1 用的是链式或者固定形状的静态草稿树——不管当前上下文是什么，每一步该生成几个候选 token 是提前写死的。但 EAGLE-2 团队观察到：**草稿 token 的接受率跟它在树里的位置关系不大，而是高度取决于具体的上下文**。有些上下文非常好猜（邮件模板、代码模板），可以多猜几层；有些句子逻辑高度不确定，猜多了也是白猜。

EAGLE-2 还有个关键发现：EAGLE 的草稿小模型自我认知非常清醒（**well-calibrated**）—— 小模型自己给出的概率分数非常靠谱，它觉得草稿 token 行，那大模型大概率也会接受。这意味着不需要额外通过大模型验证就能预判草稿的可信度。

基于这个发现，EAGLE-2 引入了**上下文感知的动态草稿树**：

1. **动态扩展**：逐层构建草稿树时，每一层只挑选"全局接受概率"（从根节点到当前节点路径上所有置信度的连乘积，记作 $V_i$）最高的若干节点继续往下展开；
2. **重排序**：树长到指定深度后，把所有候选节点按 $V_i$ 重新排序，挑出最优的那批节点拼成最终要喂给大模型验证的序列（同时构造好对应的树状注意力掩码，保证每个 token 只能看到自己的祖先节点）。

「好猜的地方多猜，难猜的地方少猜」的动态策略让 EAGLE-2 在保持无损的前提下，比 EAGLE-1 再提速 20%-40%。

### EAGLE-3："猜 token" + 训练时测试

EAGLE-1/2 有一个天花板：它们要求草稿模型去预测大模型的**隐藏层特征**。但特征预测有个天然缺陷——这些特征在训练时只被灌输了「预测下一个 token」这一个任务，携带的语义维度其实很窄。这导致草稿模型的效果很快就会饱和，**不能像大模型本身那样满足 Scaling Law 地从数据规模中获益**。

EAGLE-3 的做法是**彻底放弃特征预测，改为直接预测 token**。

但问题来了：没有了特征作为中间监督信号，信息损失了怎么办？EAGLE-3 用**多层特征融合**：不再单看倒数第二层的特征，而是把浅层（词法）、中层（句法）、深层（语义）的特征全部打包、拼接融合后喂给草稿模型。

另一个核心创新是 **training-time test（训练时测试，TTT）**：以前训练草稿模型用的是 teacher-forcing（每一步都喂给它绝对正确的标准答案），这导致模型在实际推理连续套娃生成草稿时，一旦出现微小误差就崩了。EAGLE-3 在训练阶段就去模拟推理时「多步自回归起草」的真实过程，让草稿模型提前适应"看到自己生成的、可能带误差的草稿"这一现实。

这两项改动叠加起来的效果非常明显：EAGLE-3 的草稿模型终于**迎来了属于自己的 Scaling Law**，能随数据量变大而持续变强。EAGLE-3 完美向下兼容 EAGLE-2 的动态草稿树技术，两者可以无缝叠加。

**目前 EAGLE-3 已经成为 vLLM、SGLang 等主流推理框架里的"标配"投机解码方案。**

## 三：MTP —— 投机解码"焊死"在预训练里（DeepSeek-V3, 2024 末）

如果说 EAGLE 系列代表的是**事后补课**（额外训练一个专属草稿模型挂在大模型旁边），那么 DeepSeek-V3 提出的 **MTP（Multi-Token Prediction，多 token 预测）** 则代表了另一种哲学：**投机解码这件事，能不能从预训练阶段就设计进模型本身？**

MTP 的做法是：在主干模型之后，顺序串接若干个轻量级的 MTP 模块（DeepSeek-V3/R1 官方开源版本只用了 1 个）。**在预训练阶段，大模型和 MTP 模块是同甘共苦的。** 除了常规的"预测下一个 token"，模型还要顺带预测第 2、第 3 甚至更远未来的 token。

这样做首先是为了让模型学到更具「前瞻性」的表征、提升数据效率和模型本身的能力（DeepSeek-V3 技术报告称此举本身就能提升主任务效果）。

而"投机解码"则是这套设计一个**近乎免费的副产品**：到了推理阶段，这些原本用于辅助训练的 MTP 模块可以直接拿来当草稿头使用——不需要另外训练、另外加载一个独立的草稿模型。业界在此基础上衍生出两种推理策略：

- **MTP Vanilla**：每个 MTP 模块分别负责预测未来固定偏移位置的 token
- **MTP Eagle**：借鉴 EAGLE 思路，把同一个 MTP 模块循环调用多次（"套娃模式"），契合官方只有单个 MTP 模块的情况，且推理时能最大化复用同一份 KV Cache

MTP 的意义在于**思路上的降维打击**：不需要额外的模型、额外的训练流程、额外的部署复杂度，投机解码的能力附赠在了基座模型里。DeepSeek-V3 报告给出的数据是约 **1.8 倍解码加速**，引入的算力代价几乎可以忽略。

## 四：天花板 —— 自回归的"因果性"

EAGLE-3 和 MTP 已经把「自回归式起草」这条路线打磨得相当精细，但无论怎样，它们还是逃不开一个结构性的物理限制：**草稿本身也是自回归模型，也是要一个词一个词吐出来的**。

哪怕草稿模型再小、再快，起草 $\gamma$ 个 token 依然需要老老实实完成 $\gamma$ 次连续的前向传播（$T_{draft} = \gamma \cdot t_{step}$）。想让草稿树更深、猜得更远、接受长度 $\tau$ 更大，起草的时间成本就跟着线性飙升。在效率与准确率的极限拉扯下，**自回归路线的实际加速比最终被死死锁在了 2 到 3 倍的瓶颈**。

于是研究者们的目光开始转向另一个方向：**扩散模型（diffusion）**。扩散语言模型天然支持「一步并行生成一整块 token」，不需要逐词展开。如果能把扩散模型改造成一个起草专用部件，是不是就能把 $T_{draft}$ 从"随长度线性增长"变成"几乎恒定"？

这就引出了 2026 年前后集中爆发的**第二波投机解码浪潮**：DFlash、DSpark、JetSpec。

## 五：DFlash —— "块扩散"生成草稿（UCSD, ICML 2026）

DFlash（*Block Diffusion for Flash Speculative Decoding*）是第一个把扩散模型系统性地用作投机解码「起草引擎」的工作。

它的核心思路是：大模型的中间隐藏特征里，其实已经隐式编码了关于未来若干个 token 的信息（这一论点来自另一篇论文 *Your LLM Knows the Future*）。与其让一个从零开始、对上下文一无所知的小扩散模型盲猜，不如**利用大模型的丰富特征作为强条件，去指导轻量级扩散模型的去噪过程**。

DFlash 的三个核心要素：

- **非因果 Transformer 架构**：DFlash 采用双向注意力机制，通过单次前向传播同时对整个块（如 16 个 token）进行去噪生成。这种非自回归的设计使起草延迟与生成长度解耦——一个 5 层的 DFlash 起草 16 个 token 的耗时，仍低于 1 层 EAGLE-3 起草 8 个 token 的耗时。
- **KV 注入（KV Injection）机制**：这是它和 EAGLE-3 最关键的区别。EAGLE-3 将特征拼接在输入端（容易随层数加深而信息衰减），DFlash 将大模型的隐藏特征**直接注入到草稿模型每层的 Key/Value 投影中**。这种设计确保强条件信号在深层网络中不会丢失，让草稿模型能够通过「增加层数」持续提升接受率。
- **自适应损失与锚点训练**：随机采样"锚点" token 作为每个块的起始位置来构造训练样本（贴近推理时"接上大模型刚采样出的一个真实 token，再去猜后面一整块"的真实场景）；对块内越靠前的位置赋予越大的损失权重（因为越靠前的 token 一旦猜错，后面全部作废）。

DFlash 的并行生成范式暴露出一个结构性缺陷：**块内的 token 是并行、独立生成的，缺乏彼此之间的因果依赖建模**。举个例子：草稿模型可能在某个位置独立地觉得"of course"和"no problem"这两种收尾都很合理，但由于各个位置分开打分、独立采样，可能把两个"分开看都对、拼在一起却别扭"的词拼接在一起，出现"缝合怪"草稿——这个问题后来被 DeepSeek 的 DSpark 论文明确点名，称为 **"suffix decay"（后缀衰减）**。

## 六：DSpark —— 并行草稿 + 生产级调度（DeepSeek, 2026）

DSpark 是 DeepSeek 开源的投机解码框架（配套完整训练代码库 DeepSpec），它同时解决了两个问题：**草稿连贯性** + **生产环境服务调度**。

### 半自回归架构：局部因果性

DSpark 的第一个设计是**半自回归生成（semi-autoregressive generation）**：保留一个像 DFlash 那样的并行主干（负责大部分起草工作、保证速度），但在其上再挂一个非常轻量的**串行马尔可夫头（Markov head）**：**每个位置在并行预测的同时，能"回头看一眼"紧邻的前一个 token**。

这一点点局部因果性的引入成本很低，为草稿重新引入了因果依赖，直接干掉了纯并行扩散起草里"各说各话"的不连贯现象，在几乎不影响并行度的情况下把草稿的语义质量拉回来。

### 置信度调度的验证

DSpark 给每个草稿位置配了一个**置信度头（confidence head）**，用来预测这个位置的 token"能活到最后被接受"的概率。再配合一个**硬件感知调度器（hardware-aware scheduler）**：

- **当服务器空闲时**：追求极致的单次请求延迟，让主模型老老实实验证整段草稿
- **当系统面临高并发、算力告急时**：调度器根据实时的置信度分数，只验证"大概率能中"的草稿前缀，直接砍掉后面大概率要被打回的部分，节省验证算力去服务更多并发请求

在部署上，DSpark 被设计成一个可以无缝"挂载"的插件模块。例如官方的 `DeepSeek-V4-Pro-DSpark`，它不是新模型，而是原版 V4-Pro 加装了一套独立的 DSparkBlock。**在真实生产环境的极限高并发压测下，DSpark 可以给单用户带来 57%~85% 的吞吐提速**。

## 七：JetSpec —— 因果并行树起草（阶跃星辰, 2026）

DSpark 解决了「并行起草会丢失局部连贯性」这个问题，而阶跃星辰提出的 **JetSpec** 则是把这个思路系统性地推广到了**树状起草（tree drafting）**的场景，去解决**因果性与并行树的矛盾**：

- **自回归式树起草**（如 EAGLE-2 的动态树）：每个分支上的节点都严格依赖它的祖先节点，因果关系完全正确，但树越深，起草就要越多次前向传播，延迟线性增长
- **块扩散式起草**（如 DFlash）：一次前向就能把整棵树的所有节点都并行吐出来，起草延迟几乎不变，但代价是**所有分支都是从同一份共享隐藏状态里独立打分的，节点之间没有因果约束**——大模型验证时经常发现整条路径前言不搭后语，只能拒绝。起草预算堆得越多，浪费越严重，这就是投机解码的**"扩容天花板"（Scaling Ceiling）**

JetSpec 的解法是**因果并行树起草（causal parallel tree drafting）**：训练一个极其轻量的起草头，继承 DFlash "复用目标模型多层特征 + KV 注入"的架构，在**仅仅一次前向传播中**同时计算出整棵草稿树上所有节点的 logits，但在计算这些 logits 时施加一个**树状因果注意力掩码（tree-causal attention mask）**——在这层掩码约束下，树上每个节点在并行计算时，只能"看见"原始上下文和它在树上的祖先节点，对兄弟分支和子孙节点完全隐形。

这样虽然整棵树是一次并行算出来的（起草成本几乎恒定），但每条分支内部的 token 分布都严格延续了大模型本身自回归分解的因果结构。

效果上，JetSpec 论文题目就叫"打破投机解码的扩容天花板"——在 Qwen3-8B 的 MATH-500 任务上做到 **9.64 倍加速**，在 MoE 模型 Qwen3-30B-A3B 上做到 9.45 倍，在单张 H100、真实 vLLM 服务、中低负载场景下也能拿到 6 倍以上的端到端加速。

它验证了一个此前被忽视的关键因素：**树起草要想真正"随预算扩容"，"分支内因果条件化"和"起草成本恒定"这两件事必须同时满足，缺一不可**——这正是 DFlash 这类纯并行方案在树变大后表现逐渐乏力的根本原因。

| **EAGLE-1** | 2024.1 (ICML'24) | 单层草稿模型，特征级自回归 | 外推倒数第二层特征 + token 输入消歧 | ~2-3× |
| **EAGLE-2** | 2024.6 (EMNLP'24) | 特征级自回归 + 动态树 | 用草稿置信度估计接受率，动态扩展/重排树 | 比 EAGLE-1 快 20-40%，最高 5× |
| **EAGLE-3** | 2025.3 (NeurIPS'25) | 直接预测 token + 多层特征融合 | Training-Time Test，突破数据扩展瓶颈 | 比 EAGLE-2 快 ~1.4×，最高 6.5× |
| **MTP** | DeepSeek-V3 (2024末) | 预训练内置的多头串行预测 | 投机能力"焊死"进预训练目标 | ~1.8× |
| **DFlash** | 2026 (ICML) | 块扩散，一次并行吐出整块 | KV 注入代替输入拼接 | 比 EAGLE-3 快 ~2.5×，最高 6×+ |
| **DSpark** | DeepSeek DeepSpec (2026) | 并行主干 + 轻量串行马尔可夫头 | 半自回归治"后缀衰减" + 置信度调度 | 生产环境 57%-85% |
| **JetSpec** | 阶跃星辰 (2026) | 因果并行树起草 | 树状因果掩码 | 最高 9.64×，突破扩容天花板 |

---

## 结语：一条"分久必合、合久必分"的技术演化路径

回看这条脉络，会发现一个很有意思的螺旋式演化规律：

- **EAGLE-1/2/3** 把"自回归起草"这条老路走到了物理极限——从猜特征到猜 token，从静态树到动态树，从单步训练到模拟多步的 training-time test，每一步都在榨取自回归范式里最后一点效率红利，却始终逃不开"起草成本随深度线性增长"的因果性诅咒
- **MTP** 则证明了一件事：与其在推理阶段"事后诸葛亮"地补一个草稿模型，不如从预训练的第一天起就把"预测未来多个 token"设计进模型的骨子里
- 当自回归起草撞到天花板后，**DFlash** 引入扩散模型打破了"起草必须逐词"的假设，把起草延迟拉平，但为此牺牲了 token 间的因果连贯性
- **DSpark 和 JetSpec** 几乎是从两个不同切口，不约而同地把"因果性"重新缝合回并行起草框架里——DSpark 走的是"轻量马尔可夫头补一手局部依赖 + 用置信度调度把优化战场扩展到整个服务集群"的工程路线；JetSpec 走的是"树状因果掩码让并行计算与因果分解在数学上严格兼容"的架构路线

一路看下来，投机解码的故事其实是一部持续在"起草有多快"和"猜得有多准"这两个变量之间寻找新平衡点的历史。而每一次范式突破（自回归 → 特征级自回归 → 内置预训练 → 并行扩散 → 因果并行），几乎都是因为前一代方法把自己的范式榨干到了物理极限，逼着研究者去掀桌子、换一个完全不同的角度重新出发。
